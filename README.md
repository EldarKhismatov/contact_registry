# Реестр контактов

Тестовое задание для frontend-разработчика: небольшой, но полноценный модуль со
списком контактов, созданием и редактированием карточки, поиском, сортировкой и
собственным компонентом выбора значения.

Данные обрабатываются сервером через API — фронтенд запрашивает список у backend,
а не хранит реестр в браузере.

---

## Стек

| Слой | Технологии |
| --- | --- |
| Frontend | React 19, TypeScript, Vite 7, TanStack Query 5, React Hook Form 7 + Zod 4, React Router 7, обычный SCSS без UI-библиотек |
| Backend | Node.js, Express 5, Zod 4 (та же схема валидации, что и на клиенте) |
| Хранилище | JSON-файл за интерфейсом `ContactRepository` (есть реализация в памяти) |
| Тесты | Vitest, Testing Library, Supertest |
| Инструменты | ESLint (flat config), Prettier, npm workspaces |

---

## Быстрый старт

```bash
npm install     # ставит зависимости клиента и сервера (npm workspaces)
npm run dev     # поднимает API на :3000 и веб на :5173
```

- Веб-интерфейс: <http://localhost:5173>
- API: <http://localhost:3000/api>
- Health-check: <http://localhost:3000/api/health>

В dev-режиме фронт ходит в API через прокси Vite (`/api` → `localhost:3000`),
поэтому CORS настроек не требуется.

### Остальные команды

```bash
npm run dev:server    # только API (tsx watch)
npm run dev:client    # только веб (vite)
npm test              # все тесты (сервер + клиент)
npm run typecheck     # проверка типов
npm run lint          # ESLint
npm run build         # сборка сервера (esbuild) и клиента (vite build)
npm run format        # Prettier по всему репозиторию
```

### Настройки сервера

Переменные окружения (все необязательные):

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `PORT` | `3000` | порт API |
| `STORAGE` | `json` | `json` — файл `server/data/contacts.json`, `memory` — массив в памяти процесса |
| `DATA_FILE` | `server/data/contacts.json` | путь к файлу с данными |
| `ALLOWED_ORIGINS` | `http://localhost:5173,http://127.0.0.1:5173` | origins для CORS |

При первом запуске файл данных создаётся автоматически и наполняется
демонстрационными контактами (12 записей).

## Структура проекта

```
contact_registry/
├─ package.json              # npm workspaces: client, server; общие скрипты
├─ shared/src/               # общий код клиента и сервера
│  ├─ types.ts               # Contact, ContactStatus, SortField, ApiErrorBody…
│  ├─ statuses.ts            # справочник статусов
│  └─ schemas.ts             # zod-схемы формы и query-параметров
├─ client/src/
│  ├─ api/                   # слой работы с данными: http-клиент, хуки TanStack Query, ключи кеша
│  ├─ components/ui/         # переиспользуемые кирпичи: Button, TextField, SelectPill, Modal, Banner…
│  ├─ features/contacts/     # фича: список, карточка, форма, черновики, работа с историей
│  ├─ app/                   # провайдеры и маршруты
│  └─ styles/                # SCSS: переменные темы, элементы интерфейса, стили фичи
└─ server/src/
   ├─ index.ts               # запуск приложения
   ├─ app.ts                 # сборка Express-приложения
   ├─ routes/                # HTTP-маршруты
   ├─ controllers/           # разбор запроса и ответ
   ├─ services/              # бизнес-логика: поиск, сортировка, правила записей
   ├─ repositories/          # хранилище: интерфейс + JSON-файл + память
   ├─ http/                  # ошибки API и обработчик ошибок
   └─ seed/                  # демонстрационные данные
```

Клиент разделён на слои **api → features → components/ui**: работа с данными не
знает о разметке, а переиспользуемые элементы интерфейса не знают о контактах.
Сервер разделён на **routes → controllers → services → repositories**: HTTP-слой
не содержит правил, а правила не знают про HTTP.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/statuses` | справочник статусов |
| `GET` | `/api/contacts?search=&sortBy=&sortDir=` | список контактов с поиском и сортировкой |
| `GET` | `/api/contacts/:id` | одна запись |
| `POST` | `/api/contacts` | создать запись |
| `PUT` | `/api/contacts/:id` | обновить запись |
| `DELETE` | `/api/contacts/:id` | удалить запись |

- `sortBy`: `name` \| `company` \| `status` \| `createdAt`; `sortDir`: `asc` \| `desc`.
- Поиск (`search`) ищет подстроку без учёта регистра в полях ФИО, компания, email и названии статуса.
- Ошибка валидации возвращает `400` и карту ошибок по полям:

```json
{
  "message": "Проверьте правильность заполнения полей",
  "fields": { "name": "Укажите ФИО", "email": "Укажите корректный email" }
}
```

## Как выполнены требования задания

**Список контактов.** Таблица «ФИО / Компания / Статус / Дата создания».
Поиск и сортировка выполняются на сервере: клиент отправляет параметры запроса,
они же входят в ключ кеша TanStack Query, поэтому при смене сортировки данные
перезапрашиваются, а при возврате к прежней сортировке берутся из кеша.
Сортировка переключается по клику на заголовок столбца (↑/↓), активный столбец
помечен `aria-sort`.

**Форма создания/редактирования.** ФИО и компания обязательны, email необязателен,
но если заполнен — должен быть похож на настоящий адрес, статус выбирается из
справочника. Правила описаны одной zod-схемой в `shared/src/schemas.ts` и
используются дважды: `zodResolver` в форме и проверка на сервере, поэтому клиент
и сервер не могут разойтись в трактовке правил.

**Пилюля выбора статуса.** `client/src/components/ui/SelectPill.tsx` — собственный
компонент вместо нативного `<select>`: кнопка с текущим значением, выпадающая
панель со списком вариантов, поиск внутри панели **только когда вариантов больше
восьми** (в справочнике их десять — обе ветки поведения проверяемы вручную).
Поддержаны клавиатура (↑/↓, Home/End, Enter, Esc, Tab), закрытие по клику вне,
ARIA-атрибуты `combobox` / `listbox` / `option`.

**Черновик формы.** Значения сохраняются в `localStorage` по мере ввода
(с задержкой 400 мс) и восстанавливаются при повторном открытии той же формы —
с баннером «Восстановлены несохранённые данные» и кнопкой «Очистить».
Ключи черновиков различаются по режиму и записи:
`contacts:draft:create` и `contacts:draft:edit:<id>`, поэтому черновик создания
не подмешивается в редактирование конкретной записи. В черновик попадают только
изменённые поля: при восстановлении редактирования серверные значения остаются
в силе. Черновик удаляется после успешного сохранения, а также если прошла неделя.

**Карточка в адресной строке.** Открытие карточки отражается как `?id=<id>`.
Переход по карточкам добавляет запись в историю, а кнопка «Назад» в браузере
закрывает карточку. Повторное открытие той же записи (и переключение на другую
запись, пока карточка уже открыта) обновляет текущую запись истории вместо
добавления новой — лишних записей в истории не появляется. Если приложение
открыто сразу по ссылке `?id=…`, карточка закрывается без ухода со страницы.

**Данные на сервере.** Клиент работает только через API (TanStack Query), сервер
хранит данные в JSON-файле. Хранилище скрыто за интерфейсом `ContactRepository`,
поэтому его можно заменить на SQLite, не трогая остальной код.

## Тесты

```bash
npm test
```

- **Сервер** (`server/tests`) — CRUD через supertest, валидация (пустой email
  допустим, некорректный email отклоняется, ФИО и компания обязательны,
  неизвестный статус отклоняется), поиск, сортировка, 404 для несуществующих
  записей; отдельно — юнит-тесты бизнес-логики.
- **Клиент** (`client/src`) — правила валидации, работа с черновиками в
  `localStorage` (включая раздельные ключи и очистку), компонент «пилюля»
  (открытие, выбор, порог поиска, закрытие по Escape), таблица (сортировка,
  `aria-sort`), форма с автосохранением и восстановлением черновика, а также
  поведение карточки в адресной строке (включая историю браузера).

## Решения и допущения

- **Сервер — Express**, хранилище — JSON-файл: данные переживают перезапуск,
  при этом код остаётся простым. Для тестов используется реализация в памяти.
- **Поиск и сортировка выполняются на сервере.** Так клиент работает с одним
  источником правды, а ответы кешируются по параметрам запроса.
- **Формы используют React Hook Form + Zod**, состояние списка — TanStack Query,
  адресная строка — React Router (`useSearchParams`).
- **Черновик хранит только изменённые поля** — иначе восстановление редактирования
  перезаписало бы актуальные данные записи.
- **Карточка открывается по клику на строку**, «Изменить» в таблице сразу
  открывает карточку в режиме редактирования.
- **Стили — обычный SCSS**, переменные темы вынесены в `styles/base.scss`;
  тёмная тема не реализована, так как в задании сказано, что визуальный полир не нужен.

## Что можно было бы доделать

- Тёмную тему и адаптивную вёрстку для мобильных экранов.
- Серверную пагинацию и фильтр по диапазону дат.
- Оптимистичные обновления в TanStack Query (сейчас после мутации кеш
  инвалидируется и данные запрашиваются заново).
- Хранение истории изменений записи и аудит-лог.
- Нагрузочные и e2e-тесты (Playwright) для сценариев с браузером.
